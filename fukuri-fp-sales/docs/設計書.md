# システム設計書

## 1. 全体構成

```
[情報源] 企業公式サイト / gBizINFO API / しょくばらぼ / 商工会・自治体 / 公開求人 / PR TIMES / 公式SNS
     │ （Claudeによる公開情報調査 → 調査JSON。gBizINFOはトークン設定時にAPI取得）
     ▼
[sfs.research] 検証（出典・確認日・法人番号CD）→ 企業マスターへ冪等upsert → 移動時間 → スコア → 対象区分
     ▼
[Googleスプレッドシート（正本・非公開）] 01〜10シート  ⇔  [ローカル状態 data/state/*.json（実行中のみ）]
     ▼
[sfs.outreach] 企業別営業キット（下書き）    [sfs.google_api] Gmail下書き（承認後のみ・送信なし）
     ▼ 人が確認・承認・送信
[sfs.pipeline] 活動履歴 → フォロー期限 → 日次タスク → 週次/月次KPI → 原因分析・改善案
     ▼ 導入決定
[sfs.onboarding] 案内PDF・QR・社内告知文・予約ページ・規約ひな形 → 相談件数（集計のみ）→ 月間利用実績レポート
```

- **実行基盤**：Claude Code Scheduled Tasks（クラウド）。調査・判断・コネクタ操作はClaude、検証・採点・集計・文書生成は決定的なPythonが担当する。
- **データの置き場**：リポジトリは公開のためコードのみ。企業データはスプレッドシート、資料はGoogleドライブ。個人の相談記録はこのシステムの外（予約システム・顧客管理）で管理する。
- **連携方式（2系統）**：(A) Claudeのコネクタ（Sheets/Gmail/Calendar/Drive）— 追加認証不要。(B) Python直結（サービスアカウント/OAuth）— 100社規模の同期を高速・確実にするため推奨。どちらも同じ2次元配列形式で受け渡す。

## 2. シート設計

| シート | キー | 主な用途 | 更新者 |
|---|---|---|---|
| 01_企業マスター | 法人番号 | 調査結果・スコア・営業仮説・ステータス | システム（ステータス・紹介可能性・移動時間の補完は人も可） |
| 02_優先営業リスト | 法人番号 | 確定対象×Bランク以上をスコア順（紹介可能を最上位）。毎回再生成 | システム |
| 03_営業活動履歴 | 活動ID | 接触記録・送信承認者・次回アクション・費用 | 人／システム |
| 04_法人商談管理 | 商談ID | 商談フェーズ・結果・獲得チャネル | 人 |
| 05_福利厚生導入企業 | 法人番号 | 導入企業・企業コード・予約URL・規約版 | システム／人 |
| 06_FP相談件数集計 | 年月+法人番号 | 件数のみ（個人情報なし） | システム／人 |
| 07_士業・紹介パートナー | パートナーID | 紹介元・紹介可能企業 | 人 |
| 08_営業KPIダッシュボード | - | 数式による当月KPI（B2で年月切替） | 数式 |
| 09_週次改善レポート | 週(月曜日) | 週次KPI・所見・改善案 | システム |
| 10_営業停止リスト | 法人番号 | 受信拒否・営業お断り。全処理で除外 | システム／人 |
| 11_入口提案リスト | 法人番号 | 企業ごとの最初の提案・根拠・切り口・最初の一言・接触経路。毎回再生成。01・02の「入口提案」列と対応 | システム |

法人番号が確認できない企業は `仮-<ハッシュ>` の仮キーで登録し、「法人番号未確認」と表示する。確認後に正式番号へ置き換える。

## 3. スコアリング（100点）

| 項目 | 配点 | 算定（未確認は0点） |
|---|---|---|
| 従業員規模 | 20 | 50〜100名=20／40〜49・101〜150=14／30〜39・151〜200=8／20〜29・201〜300=4 |
| 採用・人材定着 | 20 | 募集中=10、新卒＋中途=+4、定着の取組の公開=+6 |
| 福利厚生への関心 | 20 | 福利厚生の公開=8、制度が3種以上=+4、健康経営等の認定=+8 |
| アクセス | 15 | 20分以内=15／30分=12／45分=9／60分=5 |
| 意思決定者への接触可能性 | 15 | 紹介可能=15。それ以外はオーナー経営5、代表者公開2、担当部署公開3、代表電話2、公開メール/使用可能フォーム3 |
| FP相談との親和性 | 10 | 業種（最優先6/次点4/他2）、資産形成系制度あり+2、新卒・若手・子育て層+2 |

S≥80、A≥65、B≥50。対象区分：従業員数または移動時間が未確認→**追加調査**／地域外・60分超・30〜300名外→**対象外**／営業停止リスト→**営業停止**／それ以外→**確定対象**。

**移動時間**は `config/settings.yaml` の駅別所要時間表（武蔵小金井駅起点・概算）＋公式サイト記載の徒歩分数。公式サイトに駅・徒歩の記載がない企業は未確認となる。人が乗換案内で確認した値をシートに入力すれば、再調査で上書きされず確定対象に昇格する。

## 4. 営業支援
企業ごとに営業キット（営業理由／導入メリット／接触方法／初回メール／電話スクリプト／SNS／社長宛て郵送文／反論対応／フォロー計画）をテンプレートから生成。全文面に、金融商品の提案可能性・購入が条件でないこと・所属代理店・配信停止方法を明示する。
フォローのケイデンスは settings.yaml の `followup.steps`（0日メール→4日電話→10日メール→21日郵送→45日電話、最大5回）。

## 5. 導入後
`onboard-register` で企業コードを発行 → `onboard-build` で 案内PDF・QR・社内告知文・予約ページ（同意チェック3項目）・個人情報保護方針/利用規約ひな形を生成。
予約はGoogleカレンダーの予約スケジュール等を想定し、予定タイトルに `[FP相談:<企業コード>]` を付けて件数のみ集計する。企業向けレポートは件数・利用率・テーマ別件数（3件未満は秘匿）のみ。

## 6. 非機能
- **冪等性**：全シートをキーでupsert。活動IDは `法人番号-連番`、Gmail下書きは活動履歴で作成済み判定。
- **エラー処理・ログ**：CLIは失敗時に終了コード1と理由を出力。`logs/sfs_YYYYMM.log`、トークン類はマスク。
- **費用上限**：`budget`（API別の月間回数と合計金額）。超過時は `BudgetExceeded` で停止。
- **秘密情報**：環境変数／環境のシークレットのみ。`.env` と認証JSONは .gitignore。
- **テスト**：`pytest -q`。検証・採点・冪等性・営業停止・承認ゲート・秘匿・同期をカバー。

## 7. 法令・コンプライアンス上の前提（要確認事項）
- 保険業法・所属代理店規程：募集関連文書・案内資料は代理店の承認を得てから使用する。
- 特定電子メール法：公表されている事業用アドレスへの送信に限り、送信者情報と受信拒否方法を明記。拒否表明後は再送しない。
- 個人情報保護法：予約・相談の個人データは本システム外で管理。規約・方針はひな形であり、専門家・代理店の確認が必要。
